# Онтологические описания агентов ostis_ps_user_ecosystem

Двенадцать sc-агентов модуля `TrustModule` ([[ostis_ps_user_ecosystem]]):
пять реализуют правила обновления вектора доверия π_tr, один —
вычислимую часть метрик полноты провенанса, один — детектирование
аномальной частоты запросов, один — разрешение конфликта результатов по
взвешенному доверию, три — полный жизненный цикл кооперативного
исполнения подзадачи (диспетчеризация → регистрация результата →
пропагация зависимым подзадачам), один — механическое ядро
SHACL-проверок кардинальности. Код: `ostis_ps_user_ecosystem/src/agent/`.
Онтология правил: `ostis_kb_user_ecosystem/rules/`.

## Как читать эти заметки

Каждая заметка агента — по фиксированному шаблону: Идентификация →
Назначение → Компетенция → Вход → Выход → Связи → Поведение →
Безопасность → Метрики → Тесты. Раздел «Безопасность» и часть
«Limitations» в «Компетенции» получены разбором реального кода
(`m_context.IsElement(...)` — единственная проверка аргументов), а не
предположениями — это осознанные, проверенные ограничения текущей
реализации, а не общие фразы.

## Сквозные зависимости

Все двенадцать агентов используют:
- `common/float_link_io.hpp` — общий `WriteFloatLinkContent` (и
  `ReadFloatLinkContent` — все, кроме [[AgentComputePiMetric]], которому
  для подсчёта достаточно факта существования связи, и
  [[AgentRegisterPartialResult]], у которого нет числового индикатора).
- `common/relation_io.hpp` — общие `TargetOf`/`LinkByRelation` для
  поиска/создания нероле-вых бинарных отношений (`nrel_*`); появился
  при реализации [[AgentResolveByTrustWeighted]], вынесен в общий
  заголовок при повторном использовании в [[AgentDispatchReadySubtask]].
  При реализации [[AgentRegisterPartialResult]] и
  [[AgentPropagateToDependent]] туда же вынесены `SetFunctionalRelationTarget`
  (обобщение локального `SetFunctionalStatus` из
  [[AgentDispatchReadySubtask]]) и `LinkByRole` (обобщение одноимённого
  локального хелпера оттуда же) — тот же паттерн повторного
  использования при появлении второго/третьего потребителя.
- `keynodes/trust_keynodes.hpp` (`TrustKeynodes`) / `keynodes/provenance_keynodes.hpp`
  (`ProvenanceKeynodes`) / `keynodes/security_keynodes.hpp`
  (`SecurityKeynodes`) / `keynodes/integration_keynodes.hpp`
  (`IntegrationKeynodes`) / `keynodes/task_keynodes.hpp`
  (`TaskKeynodes`) / `keynodes/integrity_keynodes.hpp`
  (`IntegrityKeynodes`) — ключевые sc-элементы и классы действий.
- Базовый класс `ScActionInitiatedAgent` (sc-machine) — реакция на
  событие `ScEventAfterGenerateOutgoingArc` с элементом подписки
  `action_initiated`.
- Один и тот же C++ модуль `TrustModule` — sc-machine допускает только
  один модуль (`SC_MODULE_REGISTER`) на разделяемую библиотеку, поэтому
  [[AgentComputePiMetric]], [[AgentDetectAnomalousRequestRate]],
  [[AgentResolveByTrustWeighted]], [[AgentDispatchReadySubtask]],
  [[AgentValidateCardinalityConstraint]], [[AgentRegisterPartialResult]]
  и [[AgentPropagateToDependent]] зарегистрированы там же, несмотря на
  название.

[[AgentAggregateTrust]] зависит от результатов остальных трёх EMA-агентов
(не от [[AgentComputePiMetric]]/[[AgentDetectAnomalousRequestRate]]) —
читает их `value_link`, но не инициирует их сама (порядок вызова —
забота внешнего оркестратора). [[AgentResolveByTrustWeighted]] в свою
очередь читает тот же `trust_level`, что наполняет
[[AgentAggregateTrust]] — единственная связь по данным между
«семействами» агентов проекта.
[[AgentDispatchReadySubtask]], [[AgentRegisterPartialResult]] и
[[AgentPropagateToDependent]] независимы от остальных семи агентов по
данным — единственная тройка, оперирующая доменом «подзадачи»
(`concept_subtask`), но связаны между собой состоянием одной и той же
подзадачи σ (`nrel_subtask_status`): Dispatch переводит её
`proposed → in_progress`, Register — `in_progress → completed` (плюс
провенансный триплет результата), Propagate читает именно `completed`
как предусловие рассылки. Порядок вызова между ними — забота внешнего
кода/оркестратора, как и для EMA-агентов; сквозной тест
`test_integration_request_pipeline.cpp` воспроизводит эту цепочку
целиком (см. «Сквозной тест» ниже).
[[AgentValidateCardinalityConstraint]] тоже независим по данным —
единственный агент, оперирующий доменом «целостность БЗ»
(`concept_integrity_constraint`/`concept_integrity_violation`), и
единственный, который реализует не одно правило, а механическое ядро,
общее сразу для шести SHACL-shape'ов.

## Самостоятельный запуск агентов

`ostis_ps_user_ecosystem/scripts/run_agent.py` -- Python-скрипт поверх
py-sc-client (venv sc-web) для запуска любого из 12 агентов на живом
sc-server без C++-тестов и без браузерной JS-консоли; по умолчанию
прогоняет демо-сценарии для всех 12 агентов подряд с иллюстративными
числами из tests/test_agent_*.cpp. Подробности запуска -- в docstring
самого файла.

> [!warning] Найденный баг sc-machine: не стирайте узел действия после InitiateAndWait
> Стирание sc-узла завершённого действия (`action_addr`, после того как
> у него уже есть дуга `action_finished_successfully`/...) через
> `erase_elements` надёжно роняет sc-server целиком: необработанное
> `utils::ExceptionInvalidParams` в C++ (`libc++abi: terminating due to
> uncaught exception`), процесс sc-server завершается. Воспроизведено
> многократно при подготовке `run_agent.py`, штатной последовательностью
> запросов клиента, без единой строчки кода агентов TrustModule --
> похоже на баг во внутренней бухгалтерии sc-machine, а не в этом
> проекте. `run_agent.py` теперь сознательно НЕ стирает `action_addr`
> (см. docstring `run_action`) -- используйте тот же приём в любом
> другом скрипте/клиенте, который дёргает эти агенты извне C++-тестов.

## Сквозной тест

`ostis_ps_user_ecosystem/tests/test_integration_request_pipeline.cpp` — не
агент, а два теста, вручную цепляющих готовые агенты подряд.

**`ValidatesUpdatesAggregatesAndResolvesConflict`** — четыре агента в
рамках фрагмента `scenario_request_processing.scs`:
[[AgentValidateCardinalityConstraint]] (ровно один автор запроса) →
[[AgentUpdateTrustReliability]] (положительная обратная связь поднимает
t_rel обработавшей запрос системы с нуля) → [[AgentAggregateTrust]]
(агрегирует в trust(s,τ,h) = 0.04) → [[AgentResolveByTrustWeighted]]
(эта система выигрывает конфликт против конкурента с доверием 0.01).

**`DispatchesRegistersAndPropagatesAlongSubtaskChain`** — весь жизненный
цикл `agent_cooperative_executor` вдоль цепочки подзадач σ_dep
(уже completed) → σ → σ': [[AgentDispatchReadySubtask]] (σ назначена,
`proposed`, единственная зависимость σ_dep уже `completed` — готова к
запуску) → [[AgentRegisterPartialResult]] (система присылает результат
r, регистрируется провенанс, σ → `completed`) →
[[AgentPropagateToDependent]] (σ', зависящая от σ, получает r как вход
через inform-акт).

Оба теста показывают, что выход каждого агента правильно читается
следующим по данным — без отдельного агента-оркестратора, которого в
проекте пока нет (см. выше про [[AgentAggregateTrust]]).
