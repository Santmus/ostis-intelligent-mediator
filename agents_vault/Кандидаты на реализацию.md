## Каталог агентов (`concepts/sc_agents.scs`)

**12 агентов**. У первых 8 заданы `nrel_implements_process`/
`nrel_realizes_mapping`; у последних 4 — только
`nrel_primary_condition`/`nrel_agent_input`/`nrel_agent_output`
(менее формально специфицированы). `agent_context_updater` и
`agent_conflict_detector` не входят в список `rrel_key_sc_element`

## Легенда оценки готовности

- **ГОТОВО** — есть явная формула/алгоритм, входы/выходы понятны, реализуемо почти как есть.
- **ЧАСТИЧНО** — числовая/структурная часть есть, но зависит от неопределённых в тексте KB величин или подфункций (нужно дополнительное проектирование).
- **НЕТ** — чисто декларативный/философский текст, вычислять нечего (или задача по сути NLP/эвристика без формулы).

## Разбор по файлам

### `rules_allocation.scs` — агент `agent_task_allocator`, 4 правила

- `rule_compute_match_function` — `match(σ,s)=w_T·sim_T+w_I·sim_I+w_O·sim_O+w_C·ctx_compat+w_Q·qos_score+w_R·trust(s,τ,h)` — **ЧАСТИЧНО**
- `rule_assignment_admissibility` — `assign(σ,s) ← match(σ,s)≥θ ∧ valid(C,L_s)` — **ЧАСТИЧНО**
- `rule_coalition_optimization` — `χ*=arg max Σ match(σ,χ(σ))` при coverage∧consistent — **ЧАСТИЧНО**
- `rule_handle_no_admissible_assignment` — IF нет допустимого s THEN рекурсивная декомпозиция/integrity_violation — **ГОТОВО**

Формула match() явная, но из 6 слагаемых готов только член `trust(s,τ,h)`
(уже реализован через [[AgentAggregateTrust]]) — остальные пять
(sim_T, sim_I, sim_O, ctx_compat, qos_score) не определены в тексте.
`rule_coalition_optimization` — комбинаторная задача о назначениях без
указанного алгоритма решения.
Числовой пример: `scenario_request_processing.scs` —
`rrel_required_confidence: [0.85]` (порог θ), но само значение match()
нигде не вычислено явно.

### `rules_coalition_reconfiguration.scs` — агент `agent_coalition_reconfigurator`, 4 правила

- `rule_on_system_failure` — IF status=failed∧assigned_to∧member_of THEN исключить s, пересчитать коалицию — **ГОТОВО**
- `rule_on_resource_exhaustion` — при resource_exhausted пометить reassigned, пересчитать — **ГОТОВО**
- `rule_on_constraint_violation` — «понизить trust(s,τ,h)» без формулы величины понижения — **ЧАСТИЧНО**
- `rule_on_context_drift` — `ctx_compat(C',s) < θ_ctx` → исключить s — **ЧАСТИЧНО** (ctx_compat не определена)

Два правила-триггера (отказ/истощение ресурса) — чистая логика перехода
состояний. Два других зависят от неопределённых величин.
Числовой пример: `scenario_coalition_reconfiguration.scs` — «Понижение
доверия к intelligent_system_ranker: 0.71 → 0.58» (готовая пара
до/после, но без формулы расчёта самого понижения).

### `rules_cooperation.scs` — агент `agent_cooperative_executor`, 3 правила — **✅ реализован целиком**

- `rule_dispatch_ready_subtask` — IF assigned∧status=proposed∧∀зависимость=completed THEN status=in_progress + отправка запроса — **ГОТОВО** → ✅ реализовано, [[AgentDispatchReadySubtask]]
- `rule_register_partial_result` — при получении r создать partial_result+produces+caused_by_subtask+generated_in_context, status=completed — **ГОТОВО** → ✅ реализовано, [[AgentRegisterPartialResult]]
- `rule_propagate_to_dependent` — для каждой σ' с depends_on(σ',σ) и σ=completed сделать r входом σ' — **ГОТОВО** → ✅ реализовано, [[AgentPropagateToDependent]]

Все 3 правила — детерминированная работа с графом зависимостей и
статусами (без арифметики, но с чётким IF/THEN) — форма максимально
похожа на уже реализованный паттерн. **Самый «чистый» файл из всех** —
и единственный на данный момент, реализованный полностью (3 из 3
правил, а не механическим ядром сразу для нескольких, как
[[AgentValidateCardinalityConstraint]]).
Числовой пример: `scenario_request_processing.scs` (шаг 5) — полный
слепок структуры `partial_result`, воспроизведённый интеграционным
тестом `DispatchesRegistersAndPropagatesAlongSubtaskChain`;
`scenario_knowledge_exchange.scs` — конкретные значения payload
(r_1=42, r_2=37, r_3=51 кВт·ч) для актов FIPA-ACL.

### `rules_decomposition.scs` — агент `agent_task_decomposer`, 3 правила

- `rule_apply_decomposition_pattern` — argmax sim_T(τ_q,τ_p) по шаблонам — **ЧАСТИЧНО** (sim_T и структура шаблона не заданы)
- `rule_recursive_decomposition` — рекурсивное применение предыдущего правила — **ЧАСТИЧНО**
- `rule_check_acyclicity` — после декомпозиции запустить acyclic(depends_on) — **ГОТОВО** (классический граф-алгоритм)

Выбор/инстанцирование шаблона декомпозиции требует NLP-подобной
семантической близости и библиотеки шаблонов — не готово «как есть».
Проверка ацикличности — полностью самодостаточна.
Числовой пример: явных чисел нет, но почти каждый сценарий даёт готовые
DAG подзадач (`nrel_subtask_depends_on`) как тестовые фикстуры.

### `rules_explanation.scs` — агент `agent_explanation_builder`, 4 правила

- `rule_build_local_explanation` — создать `concept_explanation_local` по шаблону provenance — **ЧАСТИЧНО**
- `rule_build_global_explanation` — агрегировать локальные объяснения в глобальное — **ЧАСТИЧНО**
- `rule_build_contrastive_explanation` — зафиксировать различия провенансных цепочек X и Y — **ЧАСТИЧНО**
- `rule_build_counterfactual` — «минимальное изменение входа, дающее иной результат» — **ЧАСТИЧНО** (открытая алгоритмическая задача)

Все 4 правила формально заданы (триггер → создать сущность), но
ключевая операция («агрегировать», «зафиксировать различия»,
«минимальное изменение») не имеет конкретного алгоритма в тексте.
Числовой пример: `scenario_explanation_construction.scs` даёт точную
схему реифицированного акта (`explanation_act_001`/`explanation_77`),
фактически конкретизирует «шаблон» для local/global.
`scenario_recommendation.scs` — готовый контрфактический пример: «при
увеличении допуска времени на 12% оптимальным стал бы маршрут r_3».

### `rules_integration.scs` — агенты `agent_result_integrator` + `agent_conflict_detector`, 5 правил

- `rule_detect_conflict` — `conflict(res_i,res_j) ← inconsistent ∨ incompatible_context ∨ violated_constraint` — **ЧАСТИЧНО** (3 неопределённых предиката)
- `rule_aggregate_results` — выбор стратегии S с учётом trust(s,τ,h) и C — **ЧАСТИЧНО**
- `rule_resolve_by_argumentation` — построить ⟨Args,Attacks⟩, взять grounded extension — **ЧАСТИЧНО** (grounded extension — известный алгоритм, но построение Args/Attacks не задано)
- `rule_resolve_by_trust_weighted` — `w_i=trust(s_i,τ,h); r*=arg max_i w_i` — **ГОТОВО** → ✅ реализовано, [[AgentResolveByTrustWeighted]]
- `rule_validate_integration` — `∃e.explained_by(ir,e) ∧ ¬∃c.conflicts_with(ir,c)` — **ГОТОВО**

`rule_resolve_by_trust_weighted` — сильный кандидат: напрямую
переиспользует уже реализованный [[AgentAggregateTrust|trust(s,τ,h)]],
сводится к argmax по готовым числам. `rule_validate_integration` —
простая проверка наличия/отсутствия связей.
Числовой пример: `scenario_collective_decision.scs` (`[0.91]`),
`scenario_financial_decision_support.scs` (`[0.88]`),
`scenario_recommendation.scs` (`[0.78]`),
`scenario_security_breach_response.scs` (`[0.95]`) — итоговые веса
решения (но не полный набор конкурирующих w_i для argmax).

### `rules_integrity_validation.scs` — агент `agent_integrity_checker`, 7 правил (SHACL-shapes)

- `rule_validate_authorship_shape` — nrel_formulates⁻¹ minCount1 maxCount1, class concept_user — **ГОТОВО** → ✅ реализовано, [[AgentValidateCardinalityConstraint]]
- `rule_validate_subtask_status_shape` — nrel_subtask_status/priority minCount1 — **ГОТОВО** → ✅ реализовано, [[AgentValidateCardinalityConstraint]]
- `rule_validate_result_provenance_shape` — has_provenance/generated_in_context/obtained_from minCount1 — **ГОТОВО** → ✅ реализовано, [[AgentValidateCardinalityConstraint]]
- `rule_validate_integrated_result_shape` — explained_by minCount1 ∧ ¬conflicts_with — **ГОТОВО** → ✅ частично реализовано (только minCount-часть), [[AgentValidateCardinalityConstraint]]
- `rule_validate_is_capability_shape` — has_capability_profile minCount1 — **ГОТОВО** → ✅ частично реализовано (только minCount-часть), [[AgentValidateCardinalityConstraint]]
- `rule_validate_context_completeness` — 5 rrel_*_context minCount1 каждая — **ЧАСТИЧНО** (сама проверка готова, но довесок «восполнить из истории» не детализирован) → ✅ реализовано (проверка), [[AgentValidateCardinalityConstraint]]
- `rule_validate_provenance_chain` — transitive_path derived_from до user_request — **ГОТОВО** (граф-достижимость), не реализовано — принципиально другая задача (обход графа, не подсчёт дуг)

Практически весь файл — однородные, крайне низко-неоднозначные проверки
кардинальности/существования sc-связей — даже проще арифметики
trust-агентов, никаких неопределённых подфункций.
`rule_validate_integrated_result_shape` дублирует `rule_validate_integration`
из `rules_integration.scs` (пересечение файлов).
Числовой пример: явного нарушения в сценариях нет, но «позитивные»
фикстуры (валидные request/result со всеми обязательными связями) есть
почти в каждом сценарии.

### `rules_interpretation.scs` — агент `agent_request_interpreter`, 2 правила

- `rule_interpret_request` — `goal_g = ι(q.text, C)` — **НЕТ** (по сути NLU/LLM-задача, не формула)
- `rule_enrich_request` — связать q с C_domain через nrel_relevant_to — **НЕТ** (критерий релевантности не задан)

Самый слабый файл по «формульности» — ключевая операция ι(text,C)→goal
не сводится к чтению 2–5 числовых sc-ссылок в духе уже реализованных
агентов. Числового примера нет.

### `rules_provenance_completion.scs` — агент `agent_provenance_registrar`, 6 правил

- `rule_auto_record_prov_entity` — при появлении result создать prov_entity+wasGeneratedBy+wasAttributedTo — **ГОТОВО**
- `rule_auto_record_prov_activity` — при выполнении процесса создать prov_activity(actor,input,timestamp) — **ГОТОВО**
- `rule_compute_pi_metrics` — `π_proc=|{π:∃prov(π)}|/|Proc|` (аналогично π_dec, π_data) — **ГОТОВО** → ✅ реализовано, [[AgentComputePiMetric]]
- `rule_fill_missing_provenance` — реконструкция из журнала/истории/timestamp — **ЧАСТИЧНО** (эвристика без алгоритма)
- `rule_link_explanation_to_provenance` — для каждого элемента use_results/applies_rules создать wasDerivedFrom/PROV:used — **ГОТОВО**
- `rule_verify_transitive_closure` — transitive_closure(derived_from,ir) до request — **ГОТОВО**

**Самый «плотный» по готовности файл** — 5 из 6 правил детерминированы
(счёт/отношение долей, построение фиксированного набора
provenance-связей по триггеру, граф-достижимость). `rule_compute_pi_metrics`
структурно почти идентична уже реализованной агрегации trust.
Числовой пример: `scenario_explanation_construction.scs` — «π_proc=8/8=1.0»,
«π_dec=5/5=1.0», «π_data=12/12=1.0» — полностью готовый расчёт с
точными числами, прямой аналог `scenario_trust_assessment.scs`.

### `rules_security_privacy.scs` — без единого агента, 7 правил

- `rule_enforce_consent_check` — `∃c.consent_covers(c,pii)∧valid(c)` — **ЧАСТИЧНО**
- `rule_data_minimization` — payload только с необходимыми PII, лишнее — redaction — **ЧАСТИЧНО** (нет таблицы «какие PII нужны для какой подзадачи»)
- `rule_detect_anomalous_request_rate` — `rate(source,target,Δt) > k_σ·baseline_rate(target)` — **ГОТОВО** → ✅ реализовано, [[AgentDetectAnomalousRequestRate]]
- `rule_audit_log_integrity` — append-only провенанс, попытка перезаписи → нарушение — **ЧАСТИЧНО** (скорее системный инвариант, чем расчёт)
- `rule_right_to_explanation` — delivered_to∧request_type∈{...} ⇒ обязателен explained_by — **ГОТОВО**
- `rule_check_data_residency` — источники знаний должны быть в допустимой юрисдикции r — **ЧАСТИЧНО** (нет данных о юрисдикции источников в остальной части KB)
- `rule_apply_access_control_policy` — RBAC/ABAC/capability-based проверка — **ЧАСТИЧНО** (3 разных неспецифицированных под-алгоритма)

`rule_detect_anomalous_request_rate` — чистая пороговая формула,
структурно почти как trust-агенты; `rule_right_to_explanation` —
простой gate-check. Остальные 5 требуют внешних политик/таблиц.
Числовой пример: `scenario_security_breach_response.scs` — «5400
req/min, превышает базовую линию в 27 раз» — готовый вход для
`rule_detect_anomalous_request_rate`.

### `rules_user_adaptation.scs` — адаптивный интерфейс + `agent_explanation_builder`, 6 правил

- `rule_choose_presentation_template` — cognitive_load(u)≤θ_low∧desktop ⇒ detailed; >θ_high∨mobile ⇒ summary; else ⇒ card — **ЧАСТИЧНО** (cognitive_load(u) нигде не вычисляется явно)
- `rule_choose_modality` — visual-constraint ⇒ voice; preference_visual ⇒ visual; default ⇒ text — **ГОТОВО** (входы — булевы/классовые флаги, уже существующие как sc-факты)
- `rule_progressive_disclosure` — depth(provenance)>4 ∨ \|partial_results\|>5 ⇒ executive summary — **ГОТОВО** (внутренние граф-метрики, без внешних зависимостей)
- `rule_simplify_terminology_for_end_user` — end_user∧¬domain_expert ⇒ применить глоссарий — **ЧАСТИЧНО** (нужна таблица терминов, не заданная здесь)
- `rule_user_feedback_to_user_model` — обновить competence/preference/history; «пересчитать cognitive_load по последним 10» — **ЧАСТИЧНО** (сама формула cognitive_load не задана)
- `rule_context_aware_layout` — night-shift/low-light ⇒ тёмная тема + шрифт ×1.10 — **ЧАСТИЧНО** («снизить число элементов» не квантифицировано, хотя шрифт ×1.10 — чистая формула)

`rule_choose_modality` и `rule_progressive_disclosure` — чистые
пороговые/классификационные правила без внешних зависимостей.
`rule_choose_presentation_template` структурно готово, но зависит от
`cognitive_load(u)`, формула которого нигде в KB не определена (в
отличие от trust, для которого источник есть).
Числовой пример: не найден (`cognitive_load`, `θ_low/θ_high` — 0
совпадений по всем 15 сценариям); качественный пример есть —
`scenario_intelligent_tutoring.scs` содержит `preference_ivan_visual`
(флаг, релевантный `rule_choose_modality`, но не числовой).
